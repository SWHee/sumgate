# 수정 1차: Codex(GPT-6 Astra) 교차 검토에서 실행으로 재현된 결함

제약과 완료 증거 형식은 처음 지시와 같다(수정 금지 파일, git/배포 금지, 금지 표현, U+00B7 금지, 원본 체크섬). 각 결함마다 **먼저 실패하는 회귀 테스트를 추가**하고 고친다. 증상별 땜질이 아니라 아래 "원칙"을 공통 경로 한 곳에서 지키게 고친다.

## 원칙 (공통 경로에서 보장)
P1. 합산(R3)은 사건 행이 아니라 **현재 관련자 그룹 구성원 x 지급월**의 모든 유효 요청(지급 완료와 지급 진행 중 포함, 거절과 취소 제외)에서 매번 다시 계산한다.
P2. 같은 (그룹, 지급월)에 열린 사건은 항상 하나다. 접수, 회차 이동, 그룹 변경으로 겹치면 병합하고 다시 판정한다(기존 승인은 근거가 바뀌므로 무효).
P3. 지급으로 이어지는 모든 경로(실행, 은행 재처리 포함)는 같은 재검증 게이트(R7)를 지난다. 근거가 바뀌면 아직 지급 완료가 아닌 지급 작업은 취소하고 승인을 무효로 한다.
P4. 값이 없거나 `NONE`인 식별정보는 일치로 세지 않는다. 지급에 필요한 정보(마스터 등록, 정산계좌, 양수 금액)가 없으면 `확인 필요`이고 지급 작업을 만들지 않는다.

## 재현된 결함 (service 계층 직접 호출, 메모리 SQLite)
F1 [치명] 은행 반려 뒤 금액 정정(1,000,000 → 3,000,000) 후 `retry_payment`: 재검증 없이 옛 승인과 옛 금액 1,000,000으로 다시 지급되고 승인은 valid인 채 `지급 완료`가 된다. → P3.
F2 [높음] 지급 완료(D-005 1,500,000) 뒤 정정으로 D-010이 같은 그룹이 되고 D-010 새 요청 1,000,000 접수: paid 0, total 1,000,000, 전결로 실행된다. 올바른 결과는 합산 2,500,000, 영업임원. → P1.
F3 [높음] D-005의 2026-06 정산 요청(1,500,000, 7월 회차)과 2026-07 정산 요청(1,000,000, 8월 회차)이 있을 때 마감 경과로 앞의 것이 8월 회차로 이동: 같은 (그룹, 2026-08) 사건이 2개로 남아 각각 전결. 올바른 결과는 한 사건 2,500,000, 영업임원. → P2.
F4 [높음] `rules.find_groups`: 대표자, 주소, 계좌가 모두 ''이거나 모두 'NONE'인 두 거래처가 한 그룹으로 묶인다. → P4.
F5 [높음] 마스터 정산계좌가 'NONE'인 거래처의 요청이 승인, 실행되어 지급계좌 'NONE'인 지급 작업이 생긴다. → P4.
F6 [중간] 음수 금액 요청: +3,000,000과 -2,000,000이 순액 1,000,000 전결로 판정되고 -2,000,000 지급 작업이 생긴다. → 금액이 0 이하인 요청은 접수 시 `확인 필요`로 두고 합산과 지급에서 제외(P4). 차감이나 상계 기능은 만들지 않는다.
F7 [중간] 지급월 등급이 `가정`인 채로 승인과 지급 작업 생성까지 간다(TOPIC 6절 실패 조건 1). → 설계 결정: **승인이 지급 회차를 확정한다.** 승인 화면에 "이 승인은 YYYY-MM 회차 지급을 확정합니다"를 표시하고, 승인 시 해당 요청의 지급월 등급을 `확정(승인 시)`로 바꾼다. 지급 작업은 지급월이 확정된 요청에만 만든다. 승인 전 화면의 `미확인` 표시는 유지한다.

## 추가 지시
A1. 상태를 바꾸는 모든 엔드포인트에 서버 측 역할 검사를 넣는다(지금은 전결 일괄 승인, 승인, 거절만 검사). 역할별 허용 동작은 설계서 1절 표를 따른다. 모의 입력은 `모의 외부` 역할, 시나리오 실행과 초기화는 모든 역할 허용. 역할이 맞지 않으면 403과 한국어 안내.
A2. Docker 데몬이 켜졌다. `docker build`와 컨테이너 실행 후 첫 화면 200, S1 버튼 흐름까지 확인한다. 컨테이너에서 SQLite 파일이 쓰기 가능한 위치에 생기는지도 확인한다.
A3. 위 원칙으로 고친 뒤에도 S1~S3 요약과 원본 수치 테스트가 그대로 통과해야 한다. 요약이 달라지면 무엇이 왜 달라졌는지 보고한다.
