> v2 (2026-11-14): 교차 검토 2회(Codex GPT-6 Astra)에서 재현된 결함을 고치며 바뀐 규칙을 9절에 정리했다. 본문과 9절이 다르면 9절이 우선한다.

> 상위 문서: `TOPIC_W07.md`(주제, 금지사항, 검증 기준), `HACKATHON_GUIDE.md`(대회 규칙), `CLAUDE.md`(AXHub 규칙).
> 이 문서는 **어떻게 만드는지**를 정한다. TOPIC과 충돌하면 아래 0절의 수정 3건만 이 문서가 우선하고, 나머지는 TOPIC이 우선한다.
> 가상 기준일: 2026-07-01. 화면과 문서에 가운뎃점(U+00B7)을 쓰지 않는다.

## 0. TOPIC 대비 수정 3건

1. **전결도 사람 승인이다.** 전결 대상 37개 그룹은 "즉시 지급"이 아니라 영업지원팀 승인 대기로 간다. 영업지원 담당자가 일괄 승인하면 사건별 승인 기록이 남고, 그 뒤에 지급 작업이 생긴다.
2. **회차 이동은 재합산을 동반한다.** 회계 마감을 넘겨 다음 회차로 옮긴 사건은 새 지급월 기준으로 합산과 승인 경로를 다시 계산한다. 이동은 시스템의 마감 규칙으로만 일어나고 사유는 `승인 지연`으로 기록한다. 사람이 지급월을 임의로 바꾸는 화면이나 대안은 만들지 않는다(금지사항 4).
3. **경계값.** 합산액이 정확히 2,000,000원이면 전결, 2,000,001원이면 영업임원 승인이다.

## 1. 사용자와 결정

| 역할 | 화면에서 하는 일 |
|---|---|
| 영업지원 담당자 | 대기열 확인, 전결 사건 승인, 상신, AI 추출 결과 확인, 정정 사실 확정 |
| 영업임원 | 상신 사건 승인 또는 거절(사유 필수) |
| 회계 | 지급 작업 목록 확인, 지급 실행 요청 |
| 모의 외부 | 은행 회신, 대리점 회신, 마스터 정정 신고 입력 (`모의 회신` 라벨) |

로그인은 없다. 화면 상단의 역할 선택으로 전환한다(심사위원이 로그인 없이 열 수 있어야 함). 시연용 단순화라는 점을 화면에 표시한다.

## 2. 업무모델

모든 행과 화면 값에 **데이터 등급**을 붙인다: `원본` / `도출` / `가정` / `합성` / `모의 회신`. 합성 행은 ID, 적용 시점, 생성 이유를 가진다.

### 2-2. 고정 규칙 (`app/rules.py`, 순수 함수, LLM 호출 없음)
- **R1 관계.** 두 거래처의 {대표자, 주소, 계좌} 중 2개 이상 일치하면 연결. 계좌 일치는 계좌 집합의 교집합으로 본다(마스터 정산계좌, 그리고 대조 스위치가 켜져 있으면 관측 입금계좌 포함). 연결은 전이적(union-find). 쌍마다 근거 문자열을 만든다. 직접 일치면 일치 항목과 출처(마스터, 또는 입금 DP ID)를, 직접 연결이 없는 쌍이면 `전이 연결(경유: D-xxx)`을 적는다.
- **R2 지급월.** 확정된 지급월이 있으면 그 값. 없으면 정산월 다음 달(등급 `가정`, 화면에 `미확인` 표시. 근거: 원본 승인 196건 전부 다음 달 지급).
- **R3 합산.** (그룹, 지급월)에 속한 유효 요청 금액 + 같은 지급월의 기지급액.
- **R4 경로.** 합산 ≤ 2,000,000이면 영업지원팀 전결, 초과면 영업임원.
- **R5 확인 필요.** 그룹 구성원 중 마스터 정산계좌와 관측 입금계좌가 다른 거래처가 있으면 `지급계좌 확인` 작업을 만들고, 회신이 확인되기 전에는 그 사건의 지급 작업을 만들지 않는다. 지급계좌는 **마스터 정산계좌**를 쓴다는 것이 이 설계의 명시적 가정이다(원본에 지급계좌 자료 없음). 관계를 판정할 수 없는 요청(마스터 미등록 등)도 `확인 필요`다.
- **R6 승인 근거 스냅샷.** {구성원, 쌍별 관계 근거, 마스터 버전, 요청 ID와 금액, 지급월과 등급, 합계, 경로, 지급계좌}를 정규화해 해시. 승인 시 `approval.basis_hash`에 저장.
- **R7 실행 전 재검증 (나만의 확장).** 지급 작업을 만들기 직전에 현재 스냅샷을 다시 계산한다. 해시가 승인 당시와 다르면 승인을 무효로 하고 `승인 무효(재상신)` 상태로 보낸다. 무엇이 바뀌었는지(diff)를 이력과 화면에 남긴다. 근거가 그대로면 통과.
- **R8 회차와 마감 (다른 부서 영향).** 회차 = 지급월. 가정: 7월 회차의 승인 마감은 2026-07-03 17:00, 지급 실행일은 2026-07-06(원본 지급일이 매월 4~9일인 점에서 도출한 가정). 마감 시각에 승인되지 않은 사건만 다음 회차로 옮기고(사유 `승인 지연`), R3과 R4를 다시 적용하고, 회계 작업 목록을 다시 만들고, 영업에 `대리점 안내` 작업을 만든다. 이미 승인된 무관한 사건은 원래 회차에 남는다.
- **멱등성.** `rebate_id` 유일, 지급 작업 `idem_key = request_id + approval_id` 유일. 같은 요청이나 같은 회신이 다시 와도 작업이 중복되지 않는다.
- **은행 회신.** 성공이면 `지급 완료`. 반려면 `지급 반려(재처리)` + 재처리 작업. 반려가 완료로 표시되면 안 된다.

### 2-3. 상태
`접수` → `확인 필요` / `전결 승인 대기` / `상위 승인 필요` → `승인 대기`(상신됨) → `승인됨` / `거절됨` → `실행 전 재검증` → `지급 작업 생성` → `지급 완료` / `지급 반려(재처리)`. 그리고 `승인 무효(재상신)`, `다음 회차 이동`.
상태 전이는 `app/service.py`의 함수로만 일어나고, 전이마다 `event_log`에 기록한다.

### 2-4. AI의 역할 (`app/ai.py`)
- **하는 일 1: 문서 구조화.** 소명 회신, 정정 신고 문서에서 {주장, 증빙, 적용일, 대상 거래처, 미확인 항목}을 각 항목의 **원문 인용**과 함께 JSON으로 뽑는다. 코드는 인용이 원문의 정확한 부분 문자열인지 검사하고 위치(offset)를 기록한다. 원문에 없는 인용은 `근거 없음`으로 표시하고 버린다.
- **하는 일 2: 상신 문서 초안.** 입력은 코드가 계산한 사실(구성원, 관계 근거, 합계, 경로)뿐이다. 사실 표는 코드가 그리고, AI는 서술 요약만 쓴다.
- **하지 않는 일.** 관계 판정, 합산, 승인 경로, 부정 여부, 합산 면제. AI 출력은 담당자가 확인하기 전에는 어떤 판정에도 쓰이지 않는다. 확인된 정정만 `agency_version`의 새 버전이 되고, 그 뒤 코드가 다시 계산한다.
- **구현.** Anthropic API, 키는 환경변수 `ANTHROPIC_API_KEY`(서버에서만 읽음). 키가 없으면 규칙 기반 대체 추출기를 쓰고 화면에 `AI 미사용(대체 추출)`이라고 표시한다. 테스트는 키 없이 통과해야 한다.

## 3. 시연 시나리오 (각각 초기화 후 독립 실행, 한 명령으로 재실행 가능)

| 시나리오 | 입력 | 처리 | 등급 |
|---|---|---|---|
| **S1 정상** | 원본 미지급 40건 접수 | 38개 그룹 판정. 37개는 영업지원 일괄 승인 → 지급 작업 → 은행 성공 → 지급 완료. D-011/024/037 사건(3,888,097원)은 지급계좌 확인 요청 → 회신(유효) → 임원 상신 → 승인 → 재검증 통과 → 지급 작업 → 지급 완료 | 원본 + 모의 회신 |
| **S2 조건 변경** | S1과 같이 임원 승인까지 진행한 뒤, 실행 전에 정정 입력 (a) D-024 주소 이전 신고, (b) 요청 금액 정정 | (a) 마스터 새 버전 → 근거 해시 변경 → 승인 무효 → 재상신. 입금계좌 대조 덕분에 그룹과 경로는 유지되고, **왜 유지되는지**(대표자 + 입금계좌 직접 일치)를 보여준다. (b) 합계 변경 → 승인 무효 → 재상신. 무관한 거래처의 정정은 어떤 승인도 무효로 만들지 않는다. 대조 D: 재검증을 끄면 옛 승인으로 실행됐을 것임을 나란히 표시 | 합성 입력 |
| **S3 거절과 정보 부족** | 임원 거절(사유: 공유 계좌 소명 없음) | 사건 보류 → 소명 요청 작업 → 대리점 소명 회신(합성 문서) → AI 구조화 → 담당자 확인 → 재상신. 그 사이 회계 마감 경과 → **이 사건만** 8월 회차로 이동 → 새 지급월로 재합산과 재판정 → 회계 작업 목록 재생성 + 영업 `대리점 안내` 작업. 이어서 합성 7월 정산 요청 1건이 같은 그룹에 들어오면 합계가 바뀌어 다시 판정된다. 은행 반려 회신도 한 번 넣어 재처리 작업을 확인 | 합성 입력 + 모의 회신 |

필수 확장(R7)은 S2에서, 다른 부서 영향(R8)은 S3에서 실제 상태를 바꾼다.

## 4. 대조군 (화면 `대조` 탭 + 테스트)
- **A** 거래처별 판정 vs 관련자 합산 판정: 같은 40건에서 상위 승인 대상이 0건 vs 1개 그룹(3건).
- **B** 입금계좌 대조 끔 vs 켬: 그룹은 같고 D-024와 D-037의 근거가 `전이 연결` vs `대표자 + 입금계좌 직접 일치`.
- **C** 음성 대조: D-034와 D-041은 대표자만 같아 묶이지 않는다.
- **D** 승인 재사용 vs 재검증(S2).
- **E** (최소) 합성 소명 문서 3건의 정답 대비 추출 결과. 키가 없거나 미측정이면 `미측정`으로 표시하고 성과로 주장하지 않는다.
- 과거 관찰: 2026-01~05 그룹 월 합계 5건을 `관찰`로 표시(`위반` 표현 금지).

## 5. 화면 (서버 렌더링 HTML, 5초 주기 재조회로 갱신. 웹소켓 금지)
1. **대기열**: 사건 목록(구성원, 지급월, 합계, 경로, 상태, 등급 라벨, 회차). 역할별 버튼.
2. **사건 상세**: 관계 근거(쌍별), 합산 내역, 거래처별로 봤을 때의 결과(대조 A), 상신 문서 초안, 승인 또는 거절, 재검증 diff, 이력.
3. **작업함**: 부서별 작업(회계, 영업지원, 영업).
4. **모의 입력**: 은행 회신, 대리점 회신 문서, 마스터 정정, 금액 정정, 가상 시각 이동.
5. **문서**: AI 추출 결과와 원문 인용 하이라이트, 담당자 확인 버튼.
6. **대조 / 과거 관찰**, **이력**, **시나리오 실행과 초기화**.
각 구간에 `실제 작동` / `모의 처리` 배지를 붙인다.

## 6. 기술 구성
- Python 3.13, FastAPI, Jinja2, SQLAlchemy. DB는 환경변수 `DATABASE_URL`(기본값은 로컬 SQLite 파일). 배포 시 AXHub DB를 붙인다. 컨테이너 볼륨에 상태를 두지 않는다는 규칙 때문에 DB 접근은 SQLAlchemy로만 한다.
- 원본 CSV는 시작 시 읽기 전용으로 적재한다(파이프 구분, `NONE` 보존). 원본 경로: `01_참가자_배포용/04_원본데이터/`.
- 합성 입력은 `data_derived/`에 두고 `data_derived/README.md`에 파일별 등급, 생성 이유, 연결되는 원본 행을 적는다.
- 폴더: `app/`(main, rules, service, models, loader, ai, scenarios, templates), `tests/`, `data_derived/`, `Dockerfile`, `pyproject.toml`, `.env.example`, `RUN.md`(실행과 재현 방법). 주최 측 `README.md`는 건드리지 않는다.
- 한 명령 재실행: `uv run python -m app.scenarios` (초기화 후 S1~S3 실행, 결과 요약 출력, 같은 입력이면 같은 출력).

## 7. 완료 기준
1. `uv run pytest`가 모두 통과한다. 테스트는 TOPIC 8절의 9개 기준, 0절의 경계값, TOPIC 6절의 실패 조건 7개, S1~S3 전 구간을 포함한다.
2. `uv run python -m app.scenarios`가 두 번 실행해도 같은 요약을 낸다.
3. 로컬 서버에서 S1~S3를 화면 버튼만으로 끝까지 진행할 수 있다.
4. `docker build`가 성공하고 컨테이너에서 첫 화면이 열린다.
5. `app/`, `data_derived/`, `docs/`, `RUN.md`에 U+00B7이 없다. 원본 폴더의 변경이 없다(체크섬 비교).

## 8. 범위 밖 (이번 구현에서 하지 않음)
AXHub 배포와 git 커밋(사용자 확인 뒤 별도 진행), 로그인, 부정 판정, 과거 지급의 위반 판정, 지급 분할이나 지급월 임의 변경 대안.

## 9. v2 변경 (교차 검토 반영, 본문보다 우선)

| 대상 | v1 | v2 | 바꾼 이유 (재현된 결함) |
|---|---|---|---|
| R2 지급월 | 가정인 채로 지급까지 진행 | **승인이 지급 회차를 확정한다.** 승인 화면에 확정 문구를 표시하고 등급을 `확정(승인 시)`로 바꾼다. 지급 작업은 지급월이 확정된 요청에만 만든다 | 지급월 미확인 상태로 지급 작업이 생김 |
| R3 합산 | 사건에 속한 요청 + 기지급액 | **현재 그룹 구성원 x 지급월**의 모든 유효 요청에서 매번 다시 계산. 지급 완료 금액은 기지급액으로 포함 | 지급 완료 뒤 그룹이 바뀌면 기지급액이 빠짐 |
| 사건 단위 | (그룹, 지급월)마다 사건 | 같은 (그룹, 지급월)의 지급 완료 전 요청은 **항상 한 사건**. 접수, 회차 이동, 그룹 변경으로 겹치면 병합하고 기존 승인은 무효. 새 요청이 합류하면 은행 회신 전 지급 작업을 취소하고 다시 판정 | 회차 이동 뒤 사건이 2개로 갈라져 각각 전결. 지급 진행 중 사건이 옛 합산으로 지급 |
| 병합 | 요청만 이동 | 미해결 소명 요청과 확인 작업, 이전 사건의 승인과 거절 이력을 승계. 소명 확인 전에는 재상신 불가 | 병합으로 임원 거절을 건너뜀 |
| R1 관계 | 값이 같으면 일치 | 빈 값과 `NONE`은 일치로 세지 않는다 | 빈 값끼리 한 그룹으로 묶임 |
| R5 확인 필요 | 계좌 불일치, 마스터 미등록 | 추가: 정산계좌 없음, 금액 0 이하, **관계 정보 부족**(대표자, 주소, 정산계좌 중 알려진 값 2개 미만). 확인 불가 회신 뒤에는 새 확인 작업으로 재확인 | 정보가 없는 거래처에 지급 작업이 생김 |
| R7 재검증 | 지급 작업 생성 직전 | 지급으로 가는 **모든 경로**(실행, 은행 재처리)가 같은 게이트를 지난다. 근거가 바뀌면 지급 완료 전 작업은 취소 | 은행 반려 뒤 재처리가 옛 승인과 옛 금액으로 지급 |
| 멱등성 | `request_id + approval_id` | **요청당 활성 지급 작업은 하나**(`pay:request_id`). 승인과 실행은 DB 최신 상태 기준(사건 행 낙관적 잠금) | 두 세션이 번갈아 승인하면 같은 요청이 두 번 지급 |
| 역할 | 화면에서만 버튼 구분 | 상태를 바꾸는 모든 요청에 서버 측 역할 검사. 역할 쿠키가 없으면 403. 첫 화면에서 기본 역할(영업지원) 쿠키를 심는다 | 역할 없이 전결 일괄 승인 가능 |
| 등급 라벨 | 5종 | `확정(승인 시)` 추가. 관계 근거는 `도출`로 표시하고 참조한 마스터 버전별 등급을 함께 표시 | 합성 정정이 반영된 근거에 `원본` 표시 |
| 시나리오의 AI | AI 구조화 | 시나리오 실행기(S1~S3)는 재현성을 위해 항상 대체 추출기를 쓴다. 실제 AI 호출은 화면에서 문서를 개별 접수할 때 키가 있으면 쓰인다 | 설계서와 구현의 서술 불일치 |
| DB | 미정 | AXHub 앱 DB는 Postgres. `axhub.yaml`의 `database: engine: postgres` 선언으로 생기고 `DATABASE_URL`이 주입된다 | 외부 DB 드라이버 누락 |

**모델의 단순화 (한계로 명시):** 은행 회신 전의 지급 작업은 취소할 수 있다고 본다. 실제 은행 이체는 전송 뒤 취소가 어려우므로, 실제 운영에서는 전송 시점에 사건을 잠그는 단계가 따로 필요하다.
